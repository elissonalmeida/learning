# Parallel Ticket Workflow — Design Spec

## Background

This repo (`learning`) hosts multiple independent projects (currently `content-creator`); more will follow. Work so far has happened in single, long-running Claude Code sessions — including one session that used Subagent-Driven Development to run an 8-task plan end-to-end with fresh subagents per task, review after each, and a final whole-branch review. That worked well, but it has two real costs that showed up directly in that session:

1. **One giant session/context window.** A full plan's worth of dispatches, reviews, and fix loops all accumulate in one conversation, even though most of the heavy token spend actually happens inside isolated subagents (dispatch prompts, review packages, live-verification tool calls). The session itself becomes unwieldy to keep open, and hitting an account-level rate limit mid-review stalls the *entire* plan, not just one task.
2. **No way to work on more than one thing at a time as a human.** Everything ran serially inside one thread, one task after another, with the controller (not the person) deciding what happens next.

## Purpose of this project

Let a person split a plan's tasks across **multiple independent Claude Code threads/sessions**, each with a small, bounded context window, each working on exactly one unit of work at a time — while keeping the same safety properties the single-session SDD workflow already has: per-task review, a stopping point after every task, and a final cross-task review before anything ships. The person decides when and how many threads run; nothing here auto-continues on its own.

## Scope

**In scope:**
- Converting a written implementation plan's tasks into GitHub Issues ("tickets"), each carrying its dependency relationships (from the plan's own Consumes/Produces sections).
- A ticket lifecycle (`status:pending` → `status:in-progress` → `status:review` → `status:done`, plus `status:blocked`) tracked via GitHub Issue labels — the one thing every thread can check without racing against a local file.
- A single explicit "pick up the next ticket" step a thread runs, claiming exactly one unblocked, pending ticket, then working it to completion (including its own fix loop and task review) and **stopping** — never auto-continuing to another ticket.
- Per-ticket isolation via a dedicated git worktree/branch, so two threads can safely edit even overlapping files without racing on disk.
- Merge-back regression protection: full test suite on every merge-back, plus automatic flagging (and an extra targeted check) when two tickets being merged together have an interface overlap (one Consumes what another Produces).
- A persistent, repo-root `docs/superpowers/HANDOFF.md` — project-level orientation for any new thread (what's active, what's next, links to specs/plans/ticket boards), distinct from per-ticket status (which lives on GitHub, not in this file).

**Out of scope:**
- True distributed locking / atomic ticket-claiming guarantees. This is designed for a person launching a handful of threads by hand, not an unattended swarm — "check the label, then claim it" is enough.
- Automated test-impact analysis (mapping arbitrary file diffs to the "right" subset of tests to run). The test suite is cheap enough (seconds) that running it in full on every merge is simpler and just as effective.
- Changes to how a *single* thread executes a plan when there's no need to split across threads — the existing `subagent-driven-development` skill's continuous-execution model is still correct for that case and is unchanged by this spec.

## Ticket lifecycle

Each GitHub Issue represents exactly one plan task. Status is tracked with one label at a time:

- `status:pending` — not started, not blocked.
- `status:blocked` — has at least one unmet dependency (an issue in its `Depends on` list that isn't `status:done` yet).
- `status:in-progress` — claimed by a thread, work underway.
- `status:review` — implementation done, task review in progress (including any fix-loop rounds).
- `status:done` — task review clean (or findings parked with a recorded ruling), merged back into the feature branch.

A ticket's body includes a `Depends on: #N, #M` line (or `Depends on: None`), computed when the ticket is generated by comparing this task's Consumes against every other task's Produces in the same plan. A ticket starts as `status:blocked` if that list is non-empty and any listed issue isn't yet `status:done`; otherwise it starts `status:pending`.

## Ticket generation from a plan

Extends the existing `writing-plans` flow with one more step, run once after a plan is approved and saved:

1. Walk the plan's tasks in order.
2. For each task, open one GitHub Issue:
   - Title: the task's name (e.g. "Task 3: Database — slide_images table and ideas.image_folder").
   - Body: the task's full brief content (the same text `scripts/task-brief` would extract), plus a `Depends on:` line.
   - Label: `status:blocked` or `status:pending` per the dependency check above.
   - A reference back to the plan file's path, so anyone reading the issue can find the full plan/spec context.
3. Once every issue for the plan is open, do one pass updating `Depends on` references to use the real issue numbers just created (they don't exist yet during step 2, since issues need to reference each other by number).

This is a mechanical, one-shot conversion — it does not replace the plan file, which remains the source of truth for the exact code/tests each task specifies. The issue is a pointer plus a status flag, not a duplicate of the plan's content.

## Picking up a ticket (the per-thread entry point)

A person starts a new thread and explicitly invokes this step (it is never automatic). The thread:

1. Lists open issues for the target plan labeled `status:pending` (not `status:blocked` — those aren't safe to start yet regardless of how appealing they look).
2. Picks one (the person can specify which, or the thread picks the first by task order).
3. Re-checks the label is still `status:pending` right before claiming (minimizes, doesn't eliminate, the race window — acceptable per this spec's scope).
4. Relabels it `status:in-progress`, comments which thread/session claimed it.
5. Creates a dedicated git worktree/branch for this ticket, off the plan's feature branch.
6. Runs the existing implementer → task-review → fix-loop flow from `subagent-driven-development`, scoped to this one task.
7. On a clean task review (or a parked-with-ruling outcome at the fix-loop cap): runs the merge-back regression check (below), merges the ticket's worktree branch back into the feature branch, relabels the issue `status:done`, comments the commit range.
8. **Stops.** Reports completion and returns control to the person. Does not check for another `status:pending` ticket and does not start one. Starting the next ticket — same thread or a new one — is always a separate, deliberate action by the person.

If the task review finds Critical/Important issues that hit the existing 5-round fix-loop cap without resolving, the ticket is relabeled `status:review` with the parked findings recorded in a comment (mirroring the ledger pattern from `subagent-driven-development`) rather than force-marked done — the person decides how to proceed on that specific ticket.

## Merge-back regression protection

Two checks run every time a ticket's branch merges into the feature branch:

1. **Full test suite**, unconditionally. Cheap (seconds, in this codebase), catches anything already under test coverage. If it fails, the merge does not proceed — the ticket stays `status:review`/`status:in-progress` and the failure is investigated before retrying.
2. **Interface-overlap check.** Before merging, compare this ticket's task's Consumes list against the Produces list of every *other* ticket already merged into this feature branch since the plan started. If there's a match — this ticket (or an earlier-merged one) consumes something another produces — run that consuming ticket's own test file(s) again, but against the *current* state of the feature branch (not the stale branch it was originally written against). This surfaces a real signature/behavior drift as a real test failure, rather than a false pass against a fake that no longer matches reality. If the re-run fails, treat it exactly like a fresh Important finding: it enters that ticket's fix loop before the merge is considered complete.

This does not replace the plan's final whole-branch review (already established practice) — it's a faster, automated first line of defense for the specific case of two independently-developed tickets silently disagreeing about a shared interface. The final whole-branch review remains the backstop for anything subtler than an interface-overlap match (architectural drift, both-sides-consistent-but-wrong assumptions, etc.).

## HANDOFF.md

A single, always-current file at `docs/superpowers/HANDOFF.md` (repo root, alongside `CLAUDE.md` — this applies across every project in the repo, not just `content-creator`). Content:

- **Where things stand:** active plan(s), which project, current branch(es).
- **What's next:** link to the plan file and its GitHub issues/ticket board; which tickets are pending/blocked/in-progress right now (a live query against GitHub, described in words — "check issues labeled status:pending on branch X" — not a stale copy of label state, since that lives on GitHub and would drift).
- **How to resume:** which skills to invoke and in what order (`brainstorming` → `writing-plans` → ticket generation → per-thread pickup), for someone who has never seen this conversation.
- **Standing conventions a new thread needs:** brand-agnostic architecture rule, PT-PT-only rule, cost-cap discipline, "one real API test before done" rule, and a pointer to `docs/decisions.md` for the reasoning behind them — not a copy of that reasoning.
- **Explicitly not included:** full history, per-ticket status detail (GitHub is the source of truth for that), anything already written in a spec/plan/decisions/backlog file — those are linked, not duplicated.

This file is updated at the end of any thread's work session (part of the "stop" step above) and read first by any new thread before it does anything else.

## What this spec deliberately does not solve

- It does not prevent two people/threads from claiming the same ticket in the few seconds between check and claim — acceptable given this is one person orchestrating a handful of threads, not an unattended system.
- It does not guarantee two tickets touching *unrelated but adjacent* code (no Consumes/Produces overlap on paper, but subtly related in practice) will be caught before the final whole-branch review. That's an inherent limit of static Consumes/Produces analysis, not a gap unique to this design — the final review exists precisely because some things can only be caught by reading the whole diff.
